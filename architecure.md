# Architecture

This file explains the code structure of Phase 1. The implementation is kept
small on purpose: every file has one clear job, and Phase 2 can replace the
baseline parts without rewriting the whole simulator.

Note: the filename follows the requested spelling, `architecure.md`.

## High-Level Flow

The simulator follows this loop:

1. Create a scenario.
2. Create the environment: vehicles, provider vehicles, edge servers, traffic
   hotspots, and weather.
3. Place provider vehicles randomly.
4. For each simulation step:
   - generate vehicle tasks
   - build valid offloading candidates
   - remove invalid out-of-range links
   - score the remaining candidates
   - choose the lowest-score candidate
   - update queues and metrics
   - move vehicles and advance time
5. Write scenario-level and step-level CSV outputs.

## `run_phase1.py`

This is the command-line entrypoint.

Responsibilities:

- read command-line arguments
- choose scenario 1, scenario 2, or both
- create `SimulationConfig`
- run the simulation
- write CSV outputs
- print a small terminal summary

Important functions:

- `parse_args()`: reads `--scenario`, `--steps`, `--seed`, and `--output`
- `main()`: runs the selected scenarios
- `print_summary()`: prints the final table after files are written

Example:

```bash
python3 run_phase1.py
```

## `phase1/config.py`

This file contains all scenario and simulation parameters.

Important models:

- `ScenarioConfig`: stores the number of vehicles, provider vehicles, and edge
  servers for one required scenario
- `SimulationConfig`: stores shared physical/network/workload constants

Important constants:

- `SCENARIOS[1]`: 20 vehicles, 3 provider vehicles, 2 edge servers
- `SCENARIOS[2]`: 50 vehicles, 6 provider vehicles, 4 edge servers

Why this file exists:

All important numbers are in one place. This makes the simulator easier to
explain and easier to tune in Phase 2.

## `phase1/models.py`

This file contains simple data models. Most of them are Python dataclasses.

Models:

- `Position`: an `(x, y)` coordinate and a distance helper
- `Task`: one computational job generated by a vehicle
- `Vehicle`: a normal moving vehicle
- `ProviderVehicle`: a mobile helper node
- `EdgeServer`: a fixed edge computing server
- `Link`: one valid wireless hop
- `OffloadCandidate`: one possible offloading action
- `OffloadDecision`: the selected action for one task
- `StepMetrics`: metrics for one simulation step
- `SimulationSummary`: metrics for a whole scenario

Why this file exists:

The rest of the code can pass clear objects instead of loose dictionaries. That
makes the project easier to read and present.

## `phase1/environment.py`

This file represents the simulated world.

Responsibilities:

- create vehicles
- create edge servers
- create traffic hotspots
- place provider vehicles using the placement module
- move vehicles
- update weather
- generate tasks
- estimate traffic density
- estimate packet-loss probability
- expose nodes by ID

Important functions:

- `advance()`: moves the world one time step forward
- `generate_tasks()`: creates random tasks for vehicles
- `traffic_density_at()`: estimates local traffic density
- `packet_loss_probability()`: computes link loss or returns `None` if out of
  range
- `provider_average_position()`: reports average provider coordinates

Packet loss uses:

```text
base loss + distance effect + traffic effect + weather penalty
```

The exact formula is intentionally simple because Phase 1 is the baseline.

## `phase1/placement.py`

This file contains provider vehicle placement methods.

Current method:

- `random_provider_placement()`

It places provider vehicles uniformly inside the two-dimensional area.

Why this file exists:

Phase 1 requires random placement. Phase 2 can add an SDN/PPO placement function
here while keeping the environment and offloading code mostly unchanged.

## `phase1/offloading.py`

This file contains the task-offloading algorithm.

Main class:

- `TaskOffloader`

The algorithm:

1. Always add local processing as a valid candidate.
2. Add provider candidates only when the provider is in range.
3. Add direct edge candidates only when the edge server is in range.
4. Add relay candidates only when both hops are valid:
   - vehicle to provider
   - provider to edge
5. Compute delay, packet loss, expected retransmissions, deadline status, and a
   score for each candidate.
6. Choose the candidate with the lowest score.

The score is:

```text
score = delay + loss_weight * packet_loss + deadline_penalty
```

Invalid choices are removed before scoring. This is the Phase 1 version of
action masking.

## `phase1/simulation.py`

This file runs a complete scenario and writes outputs.

Important functions:

- `run_simulation()`: runs all steps and returns `SimulationSummary`
- `write_summary_csv()`: writes one row per scenario
- `write_step_metrics_csv()`: writes one row per simulation step
- `_summarize_step()`: converts individual decisions into metrics

Outputs:

- `outputs/phase1/summary.csv`
- `outputs/phase1/steps_scenario_1.csv`
- `outputs/phase1/steps_scenario_2.csv`

## Dependency Policy

Phase 1 uses only the Python standard library.

This was intentional:

- no installation step is needed
- the code runs on a clean Python 3 environment
- it is easier to explain in a course presentation
- Phase 2 can add plotting or learning libraries later

## Where Phase 2 Fits

Phase 2 can extend this structure naturally:

- replace `random_provider_placement()` with an SDN/PPO placement policy
- add Kalman-based link-quality estimation before packet-loss prediction
- add reinforcement learning for decentralized offloading
- add plotting scripts using the existing CSV outputs
- compare learned methods against this Phase 1 baseline
